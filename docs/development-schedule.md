# 开发排期与发布门禁

> 配套：[产品与技术方案](../plan.md)、[32 项 AI 开发任务](ai-development-tasks.md)。当前全部任务未开始，本文是按假设推导的计划，不是实际进度或上线承诺。

## 1. 人力与估算口径

推荐配置：

- A：1 名熟悉 TypeScript、浏览器与三维交互的开发者，负责前端与编辑器。
- B：1 名熟悉 Node、数据库、模型接口与支付的开发者，负责后端与 AI。
- P/Q：产品负责人及测试支持合计约每周 2 天，参与服务决策、目标创作者招募、画面评审和上线审核。
- AI：两条有边界的编码工作流；一次每条只做一个任务，不能代替人审、真实硬件测试或开户主体。

1 人日约 6 小时有效工程工作；每开发者每周按 5 人日容量。任务工作量 66 开发人日（A 31、B 35），不包含外部开户等待；AI 的辅助效率已经体现在估算中，不再乘一次“AI 加速系数”。

基础开发窗口 8 周、80 开发人日容量；其中 14 人日为依赖等待、评审和集成余量，分布不均，不能全部视为最后一天可用。另预留 W9—W10 共 20 开发人日的风险缓冲；未发生风险不为填满时间而新增功能。

P/Q 的约 16 人日支持不计入 66 开发人日；若负责人无法提供支持，由开发者承担将导致顺延。模型/支付/邮件/运营资质等待以实际日历时间计，可能超过两周缓冲。

## 2. 时间基准

默认使用 W1—W10 相对周，W1 从“计划批准、人员到位、代码环境可准备”的那一周开始，而不是文档创建后自动开工。

仅作日历示例：若 2026-09-14 周一启动且每周五个工作日，W1 为 09-14 至 09-18，W8 为 11-02 至 11-06，W9—W10 为 11-09 至 11-20。示例未扣除中国大陆中秋/国庆等假期及团队调休；使用该日历必须按团队实际工作日重排，不能承诺 11-06 必然上线。

W8 的目标是通过工程门禁并允许限额付费试点，不等于完成 14 天商业验证。首次获准付费试点后再观察 14 天，才能评估真实付费与第二项目复用。

### W1 和 W8 的同周顺序

- W1：A 先完成 WEB-001；B 随后做 WEB-002，再做 WEB-004。A 的 WEB-003 可在 WEB-001 后独立推进。不要把依赖顺序误读为全周所有任务同时开始。
- W6：WEB-020 的权益可使用已通过 WEB-004/018 的契约，支付真实跳转联调等 WEB-019；不能用 mock 通过宣称付款已打通。
- W8 D1—D2：B 完成 WEB-029 部署/恢复演练，A 准备内测素材和预检。
- W8 D3—D4：A 执行 WEB-030，B 支持故障诊断；外部测试者必须提前预约。
- W8 D5：先由 B/P 完成 WEB-031，批准后 A/P/Q 关闭 WEB-032。两项可各用半天评审并在事先准备的材料上完成；各自 1d 估算含前期材料准备，不要求 D5 同一人连续工作两人日。
- 若 W8 内测发现阻塞，直接进入 W9 修复，不压缩账务、授权或恢复验收。

## 4. 关键路径与并行边界

主要关键路径：

```text
WEB-001 → WEB-002 → WEB-004 → WEB-007 → WEB-008/010
→ WEB-011 → WEB-012 → WEB-017 → WEB-018
→ WEB-019/022 → WEB-025 → WEB-029
→ WEB-030 → WEB-031 → WEB-032
```

WEB-012 同时需要前端 WEB-006；WEB-030 同时需要 WEB-024、026、027、028。图中斜杠表示并行分支，不代表任选其一。

前端关键链：

```text
WEB-003/004 → WEB-005 → WEB-006/009
→ WEB-013 → WEB-015 → WEB-016
→ WEB-020/021 → WEB-026 → WEB-030
```

两人工作的前提是 WEB-004 冻结共享契约。共享文件由指定负责人整合；A 不改服务端账本，B 不直接改 Three.js 交互。`src/main.ts` 与共享 schema 同时需要修改时先协调，不让多个 AI 会话覆盖同一文件。

可以并行：界面与服务骨架、模板与登录、导出与支付、内容准备与回归测试。

不能提前算完成：依赖真实 provider 的成本、依赖真实支付开户的生产验收、依赖真实设备的编码兼容、依赖客户的可用性验证。

## 5. 阶段门禁

| 门禁 | 时间 | 必须看到的证据 | 未满足时 |
|---|---|---|---|
| G0 立项/契约 | W1末 | 源码基线、产品范围、服务决策/明确阻塞、共享 DTO | 限于 mock，不能采购/生产部署 |
| G1 网页基础 | W2末 | 无Electron编辑、五套件、简单模式、登录基础 | 修交互/兼容，不加模型范围 |
| G2 AI最小闭环 | W5末 | 创建、限定修改、撤销、刷新恢复、额度账本 | 保持内部测试，不收公开费用 |
| G3 候选版本 | W7末 | 50+10评测、浏览器、授权、支付沙箱、许可说明 | 进入修复，禁止弱化测试 |
| G4 限额收费 | W8或缓冲后 | 部署/回退、内部试用、成本预算、生产支付与主体条件、人审批准 | 只开放免费/测试额度 |
| G5 商业验证 | G4后14天 | 实际支付和第二项目复用、退款/支持数据 | 不扩大投流，修改需求或报价 |

G3 技术门槛：有效AI任务成功率至少90%、受保护字段破坏为0、关键账务/授权测试全通过、P0为0。G5 的建议样本和阈值见 plan.md，不能将小样本比例写成市场转化率。

## 6. 如果只有一名开发者

总工作量不会因为 AI 代写而消失。66 人日 / 每周5人日 = 13.2周纯任务容量；考虑上下文切换、供应商等待、联调和人审，建议完整首版按 15—18 周规划，另计重大资质或支付等待。

如果目标先做不收费演示，可约 5—6 周完成约 20 人日子集：

- WEB-001、002、003、004、005、006、007、009、010，共17人日。
- 另外约3人日做受限、带临时保护的创建/修改演示胶水，仅用于受控演示，不替代 WEB-011/013/018。
- 只允许开发者控制的模型账户、受限场景和邀请演示，无公开云 API、无真实支付、无“生产可靠”承诺。

演示子集中的胶水可能需要替换，因此不能把演示排期当作商业首版排期。若要让公众直接用 AI，身份、限额、任务保护仍不可省略。

## 7. AI 辅助开发的工作安排

每日：

1. 选择一个依赖已满足的任务，给 AI 明确路径、约束和验收。
2. 先生成/审查测试与契约，再实现小步代码。
3. 人审核数据流、异常、账务和UI行为，不能只接受摘要。
4. 运行该任务测试和必要回归，记录实际结果。
5. 更新任务状态与阻塞，不自动提交推送。

每周：

- 周一确认依赖、接口变更及外部服务状态；
- 周中做一次真实浏览器演示，不只看单测；
- 周五演示本周交付、核对模型成本和未闭合缺陷；
- 将任何新增需求放入后置池，不混入当周已承诺任务。

AI 可以承担类型、适配器、样例、测试和文档草稿；需要人重点审核计费事务、身份权限、迁移、浏览器可视结果、对外承诺和支付上线。

## 8. 风险与缓冲使用规则

| 风险 | 触发信号 | 应对 | 对排期影响 |
|---|---|---|---|
| AI不能稳定局部修改 | 保护字段改变、成功率不达标 | 缩小scope/模板，确定性编译加强 | 优先使用W9；不得直接上线 |
| 浏览器导出不兼容 | MP4不可编码、内存不足 | WebM回退、缩规格、限制资源 | 2—5开发日，实际评估 |
| 供应商不满足结构化输出 | 参数错误/重试昂贵 | 改适配或换已批准模型 | 3—5开发日，重新跑评测 |
| 支付/主体未就绪 | 开户审核或地区条件未满足 | 保持沙箱和免费试点 | 日历等待可能超过缓冲 |
| 基线或上游变动 | 测试失败、工程不兼容 | 冻结基线，单独迁移评估 | 不隐瞒为AI任务完成 |
| 任务恢复/账务竞态 | 重复扣费、额度不释放 | 停收费、先修状态机与对账 | 发布阻塞，不能降级放行 |
| 真实使用无复用 | 仅试一次、不用于项目 | 改任务范围、访谈与定价 | 产品方向重新评估 |

W9—W10 只用于明确缺陷、必要适配、上线阻塞和试点支持。若新增云保存、多人协作、任意模型、图片重建或完整订阅，必须新估算，不能放进“缓冲”掩盖范围扩张。

## 9. 周报与重排格式

每周更新：计划完成ID、实际完成ID、剩余人日、关键路径阻塞、外部审批状态、AI有效成功率、单次有效成本、资金/工程缺陷、下周范围。未验收任务继续计入剩余，不以代码行数抵扣进度。

触发重排：关键链延误超过2个工作日；供应商变更；账务语义改变；需要新数据存储；首发范围扩大。重排时同步更新三个文档及总人日，不单独修改某个发布日期。
